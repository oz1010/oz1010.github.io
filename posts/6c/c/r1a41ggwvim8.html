硬件 GPGPU 工程师学习计划

目标：从具备 CPU 流水线设计能力的数字硬件工程师，成长为能够进行 GPGPU 微架构设计、RTL 实现、功能验证、性能建模与软硬件协同优化的工程师。
建议周期：42 周；每周投入 12～20 小时。
学习方式：项目驱动为主，论文、手册、课程和开源代码为辅。

1. 学习目标与能力边界

1.1 已有基础

本计划默认已经掌握：

  • 数字逻辑设计、组合逻辑与时序逻辑。
  • Verilog/SystemVerilog RTL 编写。
  • CPU 指令执行流程与流水线设计。
  • 寄存器堆、ALU、控制逻辑、流水线寄存器。
  • 基本的握手协议、状态机、时序约束概念。
  • 基本仿真与波形调试能力。

因此不安排完整的 CPU 入门课程。需要补齐的是 GPU 特有的并行执行模型、存储系统、吞吐型微架构和验证方法。

1.2 目标能力

完成计划后，应具备以下能力：

领域目标能力
GPU 编程模型理解 Kernel、Grid、Block、Warp、Lane、SIMT、同步与内存模型
GPU 微架构能设计简化 SM、Warp Scheduler、Scoreboard、执行单元和 LSU
指令集能定义简化 GPU ISA，理解线程控制、访存、同步和特殊寄存器
存储系统能设计 Coalescer、Banked Shared Memory、Cache 接口和访存队列
并行执行理解延迟隐藏、Occupancy、Warp 切换、分支发散
RTL 验证能建立参考模型、随机测试、断言、覆盖率和差分验证流程
性能分析能构建吞吐量模型，分析带宽、延迟、资源占用和瓶颈
系统协同理解编译器、运行时、驱动、命令提交和 GPU 硬件之间的接口

1.3 推荐技术栈

  • RTL：SystemVerilog
  • 仿真：Verilator / Questa / VCS（按可用环境选择）
  • 波形：GTKWave
  • 验证：SystemVerilog Assertions、Cocotb（可选）
  • 综合与面积估计：Yosys / OpenROAD（可选）
  • 软件参考：C++、CUDA 或 HIP
  • 性能分析：Nsight Compute / Nsight Systems（有 NVIDIA GPU 时）
  • 构建与协作：Git、CMake、Make、Python

3. 分阶段学习计划

阶段 0：建立 GPU 架构全景（第 1～2 周）

学习目标

理解 GPU 的设计目标：在面积、功耗和资源约束下，通过大量线程并发隐藏访存和执行延迟，获得高吞吐率。

核心知识

  1. CPU 与 GPU 的设计取舍
    • Latency-oriented 与 Throughput-oriented
    • 控制逻辑复杂度与计算资源密度
    • 单线程性能与总吞吐量
  2. GPU 基本层级
    • Device / GPC / TPC（不同厂商命名不同）
    • SM / CU
    • Warp / Wavefront
    • Thread / Lane
  3. GPU 数据通路
    • 指令取指、派发、调度、执行、写回
    • 多 Warp 并发
    • 向量化执行与标量控制
  4. GPU 存储层级
    • Register File
    • Shared Memory / LDS
    • L1 / Texture Cache
    • L2 Cache
    • Global Memory / HBM / GDDR
  5. GPU 软件栈
    • Kernel、Runtime、Driver
    • 编译器、ISA、命令队列

实践任务

  • 选择 NVIDIA、AMD 或开源 GPU 中的一种作为主要研究对象。
  • 绘制从 Kernel Launch 到 SM 执行再到显存访问的系统框图。
  • 对比 CPU 核心与 GPU SM 的资源组织。
  • 写一份架构分析文档：执行模型、存储层级、调度方式、访存路径。

阶段验收

能够不依赖资料，解释一个 GPU Kernel 从提交到执行、访存和结束的完整过程，并说明 GPU 如何通过 Warp 切换隐藏延迟。

阶段 1：CUDA 与 SIMT 编程模型（第 3～6 周）

硬件设计者也需要理解软件实际如何使用硬件。学习 CUDA 不只是为了写 Kernel，而是为了从程序行为推导硬件需求。

核心知识

  • Host / Device 执行模型
  • Grid、Block、Thread
  • Warp 与 Warp Size
  • SIMT 与 SIMD 的区别
  • Warp Divergence
  • Thread Index 与地址计算
  • Global / Shared / Local / Constant Memory
  • Barrier、Atomic、Memory Fence
  • Coalesced Access
  • Occupancy
  • Kernel Launch Overhead

实践任务

使用 CUDA（或 HIP；没有兼容 GPU 时先用模拟环境理解语义）实现：

  1. Vector Add
  2. Matrix Transpose
  3. Matrix Multiplication
  4. Reduction
  5. Histogram
  6. Prefix Sum
  7. 简单的并行 Scan / Compaction

每个实验记录：

  • 输入规模与数据布局
  • Block / Grid 配置
  • 理论访存量和计算量
  • 实测执行时间
  • 带宽与吞吐率
  • 是否存在 Warp Divergence
  • 是否存在访存不合并或 Bank Conflict

重点理解

Warp Divergence： 同一 Warp 内线程执行不同分支时，硬件可能需要分路径执行并屏蔽部分 Lane，降低有效利用率。

Coalescing： 一个 Warp 的访存请求会根据地址分布合并为若干内存事务。访问模式直接影响显存带宽利用率。

Occupancy： 同时驻留的 Warp 数量受寄存器、Shared Memory、线程数和硬件资源限制。Occupancy 高不一定意味着性能最高，但资源不足会限制延迟隐藏能力。

阶段项目：GPU Kernel 实验集

建立统一 Benchmark 框架，支持改变数据规模、线程块大小、访问模式和算法实现，并输出 CSV 或图表。

阶段验收

能够从 Kernel 的线程组织和访存模式推断硬件行为，并通过实验验证推断。

阶段 2：GPU ISA 与执行语义（第 7～10 周）

学习目标

建立硬件与编译器之间的接口认知，为自研简化 GPU 核心定义可执行的指令集。

核心知识

  • GPU ISA 与虚拟 ISA 的区别
  • Scalar / Vector 指令
  • Predicate / Mask
  • Lane ID、Warp ID、特殊寄存器
  • Load / Store 指令
  • Branch / Barrier / Atomic
  • 地址空间与访存宽度
  • 指令编码、译码与异常语义
  • 编译器指令选择和寄存器分配的基本过程

建议研究资料

  • NVIDIA PTX ISA 文档：用于理解 GPU 虚拟 ISA 和执行语义。
  • AMD GCN / RDNA ISA 文档：用于理解另一类 GPU 指令组织。
  • RISC-V Vector Extension：用于对比向量执行模型，但不要将 RVV 与 SIMT 直接等同。
  • LLVM：观察前端 IR 到目标指令的基本流程。

实践任务 A：定义 Mini-GPU ISA

建议先定义一套小而完整的 ISA：

类别指令示例语义
算术ADD、SUB、MUL、MADLane 级整数运算
逻辑AND、OR、XOR、SHL位运算
比较SETP、CMP生成 Predicate
数据移动MOV、SPLAT寄存器与常量移动
访存LD、STGlobal / Shared 读写
控制流BRA、JOIN、EXIT分支、重汇合、线程退出
同步BARBlock 级同步
特殊寄存器S2R读取 Lane ID、Block ID 等

初版可限制为整数运算和简单访存，暂不实现浮点、纹理、Tensor Core 等复杂功能。

实践任务 B：编写指令模拟器

使用 C++ 实现：

  • 指令解码
  • Warp 状态
  • Lane 寄存器状态
  • Predicate Mask
  • Global / Shared Memory
  • 分支与退出
  • Barrier 同步

用模拟器作为 RTL 的软件参考模型。

阶段验收

  • ISA 文档完整，包含指令格式和语义。
  • 模拟器能执行 Vector Add 和 Reduction 的简化程序。
  • 能说明一条指令如何从编译结果进入硬件执行。

阶段 3：GPU 核心微架构（第 11～16 周）

这是从 CPU 流水线设计转向 GPU 硬件设计的核心阶段。

3.1 微架构模块

建议设计一个简化 SM，主要模块如下：

3.2 核心知识

Warp Scheduler

  • 每个 Warp 独立维护 PC 和执行状态。
  • 选择 Ready Warp 发射指令。
  • 处理等待访存、等待依赖、等待 Barrier 的 Warp。
  • Round-Robin、Greedy-Then-Oldest 等简单策略。
  • Scheduler 数量与 Issue Width 的关系。

Scoreboard

  • 跟踪寄存器读写依赖。
  • 检测 RAW 等数据相关。
  • 指令发射前判断源操作数是否就绪。
  • 长延迟访存期间允许其他 Warp 执行。
  • 区分 Warp 内依赖和不同 Warp 的独立执行。

Warp / Lane 状态

  • Warp PC
  • Active Mask
  • 每个 Lane 的寄存器状态
  • Thread Exit 状态
  • 分支路径与重汇合状态
  • Barrier 状态

Register File

  • 多 Bank 设计
  • 多读多写端口的面积代价
  • Bank Conflict
  • 操作数收集与写回仲裁
  • 寄存器分配对 Occupancy 的影响

执行单元

  • 多 Lane ALU
  • Integer / Floating Point 执行路径
  • Pipeline Latency 与 Initiation Interval
  • 执行单元吞吐率
  • 多 Warp 共享执行单元

3.3 RTL 实践

分模块实现：

  1. Warp Context Table
  2. Warp Scheduler
  3. Instruction Fetch / Decode
  4. Scoreboard
  5. Register File
  6. Integer ALU
  7. Predicate / Mask Unit
  8. Writeback
  9. LSU 初版接口
  10. Barrier Controller

3.4 设计参数建议

先实现小规模、容易验证的配置：

  • Warp Size：8 Lane（便于仿真，之后参数化）
  • Resident Warp：4～8
  • Issue Width：1 Warp / Cycle
  • Integer ALU：每 Lane 一个简单 ALU
  • Register：每 Lane 独立逻辑寄存器空间
  • 数据宽度：32 bit
  • 指令：先支持整数算术、比较、分支、LD、ST、EXIT

这些是教学原型参数，不代表商业 GPU 的典型配置。

阶段项目：Multi-Warp Execution Core

要求：

  • 支持多个 Warp 交错执行。
  • 某 Warp 等待访存时，Scheduler 能发射其他 Ready Warp。
  • 支持寄存器相关检测。
  • 支持 Lane Mask。
  • 支持基本分支和线程退出。
  • 能执行由 Mini-GPU ISA 编写的测试程序。

阶段验收

使用软件模拟器和 RTL 进行差分测试；至少完成算术、分支、依赖停顿和多 Warp 交错执行测试。

阶段 4：GPU 存储子系统（第 17～22 周）

GPU 的性能高度依赖访存组织。对硬件 GPGPU 工程师而言，存储子系统是必须重点掌握的部分。

4.1 核心知识

Global Memory 访问

  • Warp 访存请求收集
  • 地址生成
  • 访存合并 Coalescing
  • 对齐与事务拆分
  • Outstanding Requests
  • Load / Store Queue
  • 返回数据与 Warp 唤醒

Shared Memory

  • Banked Memory 结构
  • Bank Conflict
  • Broadcast
  • 多 Warp 访问仲裁
  • Barrier 与 Shared Memory 可见性

Cache

  • Direct Mapped / Set Associative
  • Tag / Index / Offset
  • MSHR
  • Miss Queue
  • Write Through / Write Back
  • LRU / Pseudo-LRU
  • L1 与 L2 的职责和一致性边界

显存系统

  • Memory Controller
  • Channel / Bank / Row
  • Row Hit / Row Conflict
  • Burst 与数据总线
  • 带宽、延迟和并发请求数
  • HBM / GDDR 的基本组织

4.2 RTL 实践

按难度递增实现：

  1. Banked Shared Memory
  2. Warp Memory Request Collector
  3. Coalescer
  4. Load / Store Queue
  5. 简化 Direct-Mapped Cache
  6. 多 Miss 并发处理（初版可限制 MSHR 数量）
  7. Memory Controller 模型
  8. Warp Wakeup / Replay 机制（按设计需要）

4.3 必做实验

  • 连续地址访问与跨 Cache Line 访问。
  • 相同地址访问与广播。
  • 不同 Lane 跨 Bank 访问。
  • 多 Warp 争用 Shared Memory。
  • 不同 outstanding request 数量下的吞吐量变化。
  • Cache 命中率变化对执行时间的影响。

阶段项目：GPU Memory Subsystem

输入来自多个 Warp 的访存请求，完成地址合并、Shared Memory 访问、Cache 请求和响应返回。

阶段验收

能够解释一次 Warp 访存如何变成内存事务，并能通过仿真统计事务数量、Bank Conflict、Cache Hit / Miss 和平均访存延迟。

阶段 5：多 SM、互连与 GPU SoC（第 23～28 周）

学习目标

从单个计算核心扩展到多个 SM，并理解计算资源、互连和显存控制器之间的系统级约束。

核心知识

  • 多 SM 资源组织
  • Work Distributor / Block Scheduler
  • Kernel / Grid 任务分配
  • SM 与 L2 的互连
  • Crossbar 与 NoC
  • Ring / Mesh 基本拓扑
  • Router、Virtual Channel、Credit Flow Control
  • Memory Partition 与 Channel
  • 原子操作与跨 SM 同步
  • 多 SM 负载均衡

实践任务

  1. 将单 SM 复制为 2～4 个 SM。
  2. 实现简单 Block Distributor。
  3. 建立共享 L2 或简化共享内存端口模型。
  4. 设计 Crossbar，观察端口数量增长带来的复杂度。
  5. 可选：实现 2D Mesh NoC 的 Router 和链路流控。
  6. 构造多个 SM 同时访问显存的流量测试。

阶段项目：Multi-SM GPGPU SoC

系统至少包含：

  • 2 个 SM
  • Block Distributor
  • 共享 L2 简化模型
  • Memory Controller 模型
  • Host 命令提交接口
  • 性能计数器

阶段验收

能够运行多个 Block，验证任务分配、数据返回和系统级吞吐量；能够分析 SM 数量增加后瓶颈是否转移到互连或显存。

阶段 6：验证、综合、PPA 与性能建模（第 29～34 周）

6.1 验证方法

GPU 验证的复杂度来自大量 Lane、Warp 并发、分支路径、访存乱序返回和同步语义。

重点掌握：

  • Testbench 分层
  • Directed Test
  • Constrained Random
  • Reference Model
  • Differential Testing
  • SystemVerilog Assertions
  • Functional Coverage
  • 随机种子复现
  • 波形与失败最小化
  • Deadlock / Liveness 检查

6.2 必测场景

  • 多 Warp 同时 Ready。
  • 同一 Warp 内寄存器依赖。
  • 不同 Warp 的执行交错。
  • 部分 Lane 退出。
  • 分支发散和重汇合。
  • Barrier 前后线程状态。
  • Load 返回乱序。
  • 多 Warp 访存竞争。
  • Shared Memory Bank Conflict。
  • Cache Miss 与 MSHR 满载。
  • NoC 背压与请求阻塞。

6.3 综合与 PPA

掌握：

  • 综合前后面积变化
  • 组合路径与关键路径
  • 时钟频率与流水级数
  • SRAM Macro 与寄存器阵列的差异
  • 多端口 Register File 的代价
  • 扇出、仲裁器和 Crossbar 的时序影响
  • 面积、功耗、性能之间的权衡

6.4 性能模型

建立简化 Roofline Model：

  • 算术强度 Arithmetic Intensity
  • 峰值计算吞吐量
  • 峰值内存带宽
  • 计算受限与带宽受限
  • Latency Hiding
  • Occupancy 与可运行 Warp 数
  • Scheduler 发射效率
  • Memory Coalescing 效率

建议采集的硬件计数器：

  • Active / Eligible / Issued Warp
  • Warp Stall Cycles（按原因分类）
  • ALU Utilization
  • LSU Utilization
  • Global Memory Transactions
  • Shared Memory Bank Conflicts
  • Cache Hit / Miss
  • Outstanding Requests
  • NoC Throughput / Backpressure
  • Kernel Cycle Count

阶段项目：验证与性能评估平台

建立自动化流程：

阶段验收

  • 回归测试可自动执行。
  • 关键模块有断言和覆盖率。
  • 随机测试失败可以复现。
  • 有至少 3 组微架构参数对比报告。
  • 能根据性能计数器定位至少一种执行瓶颈。

阶段 7：综合毕业项目（第 35～42 周）

项目：MiniGPGPU

实现一个可仿真运行的简化 GPGPU 原型。

功能范围

必需功能

  • 自定义 Mini-GPU ISA
  • 软件指令模拟器
  • 多 Warp 执行
  • Warp Scheduler
  • Scoreboard
  • Lane Mask
  • Integer ALU
  • Global Memory 接口
  • Shared Memory
  • Coalescer
  • 简化 Cache
  • 2 个或更多 SM
  • Block Distributor
  • 性能计数器
  • RTL 与参考模型差分验证

可选增强

  • FP32 ALU
  • Atomic Add
  • Barrier 完整语义
  • 简化 NoC
  • L2 Cache
  • 简化 DMA
  • Tensor / Matrix 运算单元
  • 更复杂的 Warp Scheduler
  • 简化命令队列和 Host 接口

建议验收 Kernel

  1. Vector Add
  2. SAXPY
  3. Reduction
  4. Matrix Transpose
  5. Tiled Matrix Multiplication
  6. Histogram（可选，涉及 Atomic）
  7. Shared Memory Bank Conflict 测试

最终交付物

4. 重点知识专题

以下专题不必等到主计划结束才学习，应在相关阶段穿插深入。

4.1 SIMT 与 SIMD

需要真正理解：

  • SIMD：一条向量指令显式操作多个数据元素。
  • SIMT：软件以线程为抽象，硬件通常将线程组织为 Warp / Wavefront 进行协同执行。
  • Lane Mask 如何控制有效线程。
  • 分支发散如何影响执行效率。
  • 不同 GPU 架构如何处理分支重汇合。

4.2 Warp Scheduler 与延迟隐藏

建议重点研究：

  • Round-Robin Scheduler
  • Greedy Scheduler
  • Two-Level Scheduler
  • Ready Warp 判定
  • Scoreboard
  • Long-Latency Operation
  • Warp Stall Reason
  • Scheduler 数量、发射宽度和执行单元数量之间的关系

核心问题：当一个 Warp 因访存或数据依赖停顿时，硬件如何选择其他 Warp 保持执行单元繁忙？

4.3 Register File

GPU Register File 往往是面积、功耗和时序的重要组成部分。

重点研究：

  • 每线程寄存器数量
  • 每 SM 寄存器总量
  • 多 Bank 组织
  • 读写端口冲突
  • Operand Collector
  • Bank Conflict
  • Register Allocation 与 Occupancy
  • 寄存器溢出到 Local Memory 的影响

4.4 Memory Coalescing

从 Lane 地址集合出发，推导需要多少个内存事务：

  • 连续访问
  • 固定步长访问
  • 非对齐访问
  • 跨 Cache Line 访问
  • 部分 Lane 有效
  • 不同数据宽度

建议自己实现 Coalescer，而不是只停留在 CUDA 编程层面。

4.5 Shared Memory

重点掌握：

  • Bank 数量与地址映射
  • Bank Conflict 的产生条件
  • Broadcast 行为
  • Padding 优化
  • 多 Warp 并发访问
  • Barrier 的硬件实现

4.6 GPU 性能模型

对每个 Kernel 至少分析：

  • FLOPs
  • Bytes Transferred
  • Arithmetic Intensity
  • Theoretical Peak Throughput
  • Memory Bandwidth
  • Occupancy
  • Warp Issue Efficiency
  • Stall Cycles

不能只以仿真周期数判断架构优劣，还要结合面积、频率、带宽和资源利用率。

6. 项目开发组织方式

建议从第一周开始采用小步迭代，所有设计决策都留下文档和实验数据。

推荐仓库结构：

每个迭代建议包含：

  1. 明确一个可验证的微架构目标。
  2. 更新模块接口和设计文档。
  3. 编写或更新参考模型。
  4. RTL 实现。
  5. 定向测试和随机测试。
  6. 差分验证。

  • 关键状态转换有断言。
  • 回归测试通过。
  • 关键性能指标有数据。
  • 已知限制明确记录。

7. 硬件资源与工具建议

7.1 初期不需要高端 GPU

前期可以通过 RTL 仿真、软件模拟器和公开资料学习 GPU 架构。CUDA 实验阶段再准备一张支持 CUDA 的 NVIDIA GPU，或使用可访问的远程 GPU 环境。

7.2 建议环境

  • Linux 环境优先；Windows 用户可使用 WSL2。
  • 16～32 GB 内存适合初期 RTL 仿真和开发。
  • 大型 GPU 仿真可能需要更多内存和较长运行时间。
  • 有条件时使用 FPGA 做后续原型验证，但不要把 FPGA 作为入门前置条件。

7.3 工具选择原则

  • 先用 Verilator 建立快速回归。
  • 熟悉 SystemVerilog Assertions。
  • 用 GTKWave 定位时序和状态问题。
  • 用 Yosys 做基础综合观察。
  • 有条件再引入商业仿真器、形式验证和完整物理设计流程。

8. 学习优先级与常见误区

最高优先级

  1. SIMT 执行模型。
  2. Warp Scheduler 与 Scoreboard。
  3. Register File 组织。
  4. Coalescer 与 Shared Memory。
  5. 多 Warp 延迟隐藏。
  6. GPU 性能模型。
  7. GPU RTL 验证。

第二优先级

  • Cache / MSHR
  • 多 SM 互连
  • Memory Controller
  • NoC
  • FP32 / FP64 执行单元
  • 编译器与 ISA 深入协同

后续进阶

  • Tensor Core / Matrix Engine
  • 高级缓存一致性
  • 多 GPU 互连
  • HBM 控制器与 PHY
  • Chiplet GPU
  • 功耗管理与 DVFS
  • 高级形式验证与物理设计优化

常见误区

  • 把 GPU 当成“很多个 CPU 核心”：GPU 的执行、调度和存储组织具有明显的 SIMT 特征。
  • 只学习 CUDA，不学习硬件：会写 Kernel 不等于能设计 GPU。
  • 只实现 ALU，不实现调度和访存：真正的 GPU 性能很大程度取决于并发调度和存储系统。
  • 认为 Occupancy 越高越好：高 Occupancy 是隐藏延迟的手段，不是性能目标本身。
  • 忽略 Register File 成本：多端口、大容量寄存器堆会显著影响面积、功耗和时序。
  • 只看功能正确，不做性能计数：没有可解释的数据，就难以判断微架构是否有效。
  • 过早实现完整 GPU：先完成小规模、可验证的 MiniGPGPU，再逐步扩展。

10. 路线建议

对于已经具备 CPU 流水线设计能力的人，最有效的切入点不是重新学习 CPU，而是：

  1. 用 4 周理解 CUDA / SIMT，建立 GPU 软件行为直觉。
  2. 用 4 周定义 ISA 和软件参考模型。
  3. 用 6 周实现多 Warp 执行核心。
  4. 用 6 周实现访存子系统。
  5. 用 6 周扩展多 SM 和系统互连。
  6. 用 8 周集中进行验证、性能建模和优化。
  7. 用 8 周完成综合原型。

最重要的学习成果应当是一个可运行、可验证、可测量的 MiniGPGPU，而不是看完多少门课程或读完多少篇论文。

在项目推进过程中，始终围绕三个问题做设计：

  • 正确性：并发线程、分支、同步和访存是否符合定义的执行语义？
  • 性能：计算单元是否有足够的 Ready Warp，存储系统是否能持续供数？
  • 成本：调度器、寄存器堆、端口、互连和缓存带来的面积、功耗与时序代价是否合理？
