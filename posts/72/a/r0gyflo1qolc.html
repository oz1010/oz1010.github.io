Linux驱动-VeloceStrato仿真USB驱动指南

发表于 2026-11-11 更新于 2026-11-19 本文字数： 7.3k 阅读时长 ≈ 26 分钟

适用范围与验证架构

本文基于 USB Host/Device 仿真测试记录整理，面向 Linux USB 驱动、裸机软件及 SoC 验证工程师，覆盖 Veloce Strato 工程组织、启动、USB 裸驱测试、功能安全注错和波形调试。

适用边界：工程命令来自原始测试环境，不是所有 Veloce 版本的通用接口；Linux 观测及 DMA 原则由公开资料补充。内部组织、芯片型号、人员、账号、服务器、仓库、绝对地址及 RTL 层级已泛化，不保留原始截图。文中 <…> 均为待替换项；建议目录或伪代码不代表已交付文件。

系统组成

层次主要职责排查重点
Strato 硬件模型执行 DUT RTL，提供时钟、复位、存储器及互连模型设计标签、资源布局、信号可见性
Linux 仿真服务器与 velrun加载模型、运行 Tcl、控制时钟、采集 trace工具版本、环境变量、会话和资源状态
VirtuaLAB / USB 协同模型连接 DUT 与虚拟 USB 对端，提供协议观测角色、端口、连接时序、模型版本
QEMU / 虚拟机在设备模式验证中运行外部 Host 软件栈Guest 镜像、协同主机、设备枚举
安全核固件完成早期初始化并释放应用核ROM/RAM 镜像、链接与加载地址
应用核裸驱初始化 USB、构造事务、执行注错并检查中断MMIO 宽度、DMA、用例前后状态

Strato 属于硬件仿真平台，不应与纯软件指令模拟器混淆。Siemens 当前公开资料描述的是更新一代 Strato CS；可用于理解平台定位，不能据此推断旧版工程的 AVB 数量、命令或 trace 限制。[1]

角色必须一致

DUT 角色配套工程与对端软件对象
USB HostHost 版硬件模型 + 虚拟 USB DevicexHCI 控制器、设备枚举、Command/Transfer/Event Ring
USB DeviceDevice 版硬件模型 + QEMU 等外部 HostDWC3 设备控制、端点命令、TRB、设备事件缓冲区

不能用 Device 初始化流程验证 Host 工程，反之亦然。 原始记录中，设备控制软复位和事件缓冲区配置异常在切换为匹配的 Device 工程后不再出现；因此应先核对角色，再分析寄存器、链路或安全机制。

Strato 工程结构

交付工程与用户 shadow

原始环境通过 make shadow 创建用户运行空间。以下为脱敏后的关键关系；comp/、同级 swfile/ 及镜像相对引用是使用重点，其余目录随交付版本变化。

comp/run.tcl 通常通过 ../swfile/ 引用镜像。不要将 swfile/ 误放到 comp/ 下，也不要把某版本的存储器实例路径直接复制给另一版本。

裸驱与启动固件

建议把一次可复现实验的硬件标签、工具版本、固件版本、构建配置、镜像校验值、run.tcl、AVB 列表、用例表和日志一并归档。文件名相同不代表镜像兼容。

环境准备与 Strato 使用

登录与资源选择

  1. 按管理要求预约仿真资源，经授权通道登录仿真服务器；图形界面需要 X11 转发或远程桌面。
  2. 使用与交付工程匹配的 shell。原环境的 SourceMe 按 C shell 流程加载，不要混用 Bash 的 export 与 C shell 的 setenv。
  3. 跨主机认证采用平台批准的 SSH 密钥或代理方案，不要复制私钥到各台服务器。
  4. 加载工程环境后，使用已提供的 free_avb_info 或资源管理工具查询空闲 AVB。
  5. 同时检查 AVB 数量、顺序、Module 邻接和工程专用约束，不能只检查“空闲数量足够”。

原 USB 工程存在跨 Module 或特定 AVB 组合无法启动的记录，也出现过较小工程可运行而 USB 工程不可运行的情况。这属于交付版本及映射约束，不能概括为所有 Strato 都要求同一数量、偶数起始或连续编号。

USB 裸驱测试

建议验证顺序

按“最小访问 → 基础功能 → 真实 DMA → 注错 → 回归”推进：

  1. MMIO 冒烟：读取合法且无副作用的标识/状态寄存器，核对访问宽度。
  2. 基础初始化：验证时钟、复位、角色、PHY/虚拟链路和普通中断。
  3. 控制传输：完成枚举，核对描述符与 EP0 请求。
  4. 数据传输：执行有明确内容、长度和方向的传输，核对完成事件及数据。
  5. 功能安全：为已证实经过目标通路的事务增加 parity 注错。
  6. 独立性回归：冷启动单条、顺序全量、重复执行，比较前后状态。

普通 USB 事务尚未跑通时，不要将等待超时直接归因于 parity 或互连错误。上述顺序是建议的验证层次，不表示原记录覆盖了全部 USB 传输类型或一致性认证。

Host 与 Device 分开初始化

Device 路径：配置 DWC3 设备模式、执行设备软复位、配置设备事件缓冲区和控制端点，再配置数据端点与 TRB，启动设备并与 Host 枚举。

Host 路径：配置主机模式与端口，初始化 xHCI 的命令环、事件环及设备上下文，处理端口变化并完成枚举，再提交传输并检查完成事件。

DWC3 设备模式的 DCTL、GEVNTADRLO/HI 及端点命令，不能代替 xHCI Host 初始化。代码使用同样的“TRB”术语，也不代表两套控制器接口和事件格式相同。

32 位寄存器访问

原记录确认的一项根因是：在 AArch64 构建中，用 volatile unsigned long * 实现名义上的 32 位位操作，实际生成了 64 位 MMIO 访问，导致 Synchronous Abort。指针本身宽度不是问题，被解引用的数据类型决定访问宽度。

对 W1C/W1S、读清除、自清零及写保护寄存器，应按字段定义访问，不能通用地执行读改写。解锁密钥、写保护范围及回锁顺序也必须随当前寄存器表确认。

DMA、缓冲区与互连路径

区分 CPU 虚拟地址、CPU 物理地址和设备 DMA/总线地址；存在 SMMU 或桥接映射时，它们不一定相同。[3]

  • 控制器使用 DMA 地址，CPU 指针不能直接写入 DMA 寄存器。
  • Event Buffer、TRB 和数据区分别检查大小、对齐、高低地址及地址可达性。
  • 非一致性内存需要正确的 cache clean/invalidate；内存屏障不能代替缓存维护。
  • 一致性 DMA 内存仍可能需要发布顺序屏障，例如先写描述符内容、再提交有效位。[3]
  • Linux 实现使用 DMA API，检查映射失败并管理映射生命周期；裸机按 BSP 的等价机制实现。
  • CPU 校验缓冲区内容前，先确认 DMA 完成并取得内存访问所有权。

缓冲区位置决定测试通路。 原记录中，部分用例要求 USB DMA 访问 SRAM 才能经过目标互连分支；虽然上层选择了 SRAM，初始化函数却又强制恢复默认缓冲区，导致注错始终无法触发。修复应做到：

  1. 用例显式选择 DDR/SRAM 等内存类型。
  2. 初始化函数尊重该选择，不再次写死默认类型。
  3. 事件区、TRB 和数据区逐一打印最终地址。
  4. 在 RTL 波形中确认真实总线地址和路由，而不只相信选择变量。
  5. 对需要重新初始化的用例，独立调用 probe/prepare，避免沿用上一条描述符。

虚拟存储设备

采用 Bulk-Only Transport（BOT）的模型中，CBW 为 31 字节、CSW 为 13 字节；不要因 C 结构体填充而扩大线上长度。核对 signature、tag、传输长度、方向、LUN、命令块长度及状态/残余长度；CBW signature 数值为 0x43425355，线上采用小端序。

先使用 INQUIRY、READ CAPACITY 等命令核对命令阶段、数据阶段和状态阶段，再做读写数据比对。此流程针对 BOT，不适用于 UAS，也不能把某个模型的 SCSI 响应固定为所有设备的预期。

Parity 与功能安全验证

通路分类

访问来源目标通路合适的触发方式
CPU 寄存器读写配置 NoC → AXI/AHB 转换 → USB 控制器对合法寄存器执行指定读/写
CPU 寄存器读写配置 NoC → APB → USB CSR/PHY 配置模块使用该模块的专用访问流程
USB DMAUSB 控制器 → 局部互连 → 系统 NoC控制器读描述符、读/写传输数据或写事件
USB DMA系统 NoC → SRAM/DDR 对应分支同时选择正确地址区和真实 USB 事务

rdata/wdata 应从被测总线主设备的视角解释，不等同于 USB 的 IN/OUT。CPU 执行一次 readl() 也不能替代 USB DMA 主设备的读事务。

用例表必须表达的信息

每条用例至少记录：路径、读写方向、注错源、检测端、注错/使能/mask/状态/清除寄存器及位域、写保护要求、中断域与编号、缓冲区位置、触发操作和额外初始化。明确位图与位序号的区别，避免重复移位。

使用稳定的路径标识关联需求与结果，不依赖易变的数组序号。中断号应注明是硬件 INTID、SPI 相对编号还是软件映射编号；不要不加区分地使用“编号加固定偏移”。

标准测试闭环

  1. 建立基线：停止注错，清理旧状态，登记 ISR，确认无异常中断。
  2. 准备事务：完成当前用例所需的控制器、缓冲区和对端初始化。
  3. 配置注错：按写保护流程设置检测使能和目标注错位，检查必要的读回。
  4. 触发访问：执行确实经过目标通路的 MMIO 或 USB DMA 事务。
  5. 检查上报：分别验证检测端状态、汇聚状态和目标 ISR，排除其他错误源。
  6. 检查屏蔽：仅屏蔽目标上报路径，确认不再进入目标 ISR；原始状态是否保持应按手册区分于屏蔽后状态。
  7. 检查解屏蔽：按中断类型，验证待处理状态重新上报，或清状态后重新注错并触发；不假设所有边沿中断都会因解屏蔽自动重发。
  8. 检查清除：停止持续注错后按定义清状态，并完成必要的中断应答，防止立即重新置位。
  9. 检查 disable：关闭被测安全机制，重复有效的注错与事务，确认不产生该机制预期禁止的状态/安全中断。
  10. 恢复环境：还原使能、mask、写保护及链路状态，检查下一条用例可独立启动。

Mask 极性和多级汇聚关系必须显式配置。不要套用“写 1 一定屏蔽”，也不要为调试把所有 mask 写全 1 后当作正式结论。Disable 的负向验证要确认事务确实发生，不能以“业务未运行、所以无中断”判通过。

用例独立性与结论边界

原记录中，部分用例只有在前一条已初始化控制器、切换缓冲区或修改 mask 后才能通过。应同时执行冷启动单条、顺序全量和重复执行；若断开连接后仍无法重跑，说明还需要清理控制器、描述符或协同模型状态。

原记录包含早期小集合顺序通过、扩充集合后仍有失败，以及后续重新梳理用例后的样片通过结果。这些结果不等于同一版 Strato 全量仿真通过，也不能用样片通过替代仿真覆盖证明。 自动生成的注错表仍需逐项校验通路和位域，失败项不得无依据删除或统计为通过。

与 Linux 驱动的对应关系

裸驱确认 MMIO、IRQ 与 DMA 基础链路后，再迁移到 Linux：核对固件描述中的寄存器、IRQ、时钟、复位、PHY 和 dr_mode；通过内核 MMIO/DMA API 管理映射、缓存和所有权；按 Host/Device 角色使用对应 USB 框架。不要在 Linux 中另行复制裸驱的硬编码初始化去与既有驱动竞争硬件。

仿真频率、trace 采集和日志可能显著增加墙上时间，但硬件超时、Guest 定时器及协同模型也有各自时间语义。保持有界等待并记录仿真进度，不以无限重试掩盖未完成的事务。

执行与归档清单

  • 启动前：确认硬件标签、AVB、用户 shadow、工具版本、启动介质、镜像及 run.tcl 配套。
  • 测试前：确认角色与对端、基础枚举、32 位访问器、DMA 最终地址、用例通路、mask 极性及 ISR。
  • 注错时：保留事务证据、原始/汇聚状态、中断计数，以及屏蔽、清除、disable 的负向验证。
  • 回归时：分别记录冷启动单条、顺序全量和重复执行；失败、未执行、不适用分开统计。
  • 归档时：保存配置、镜像校验值、用例表版本、命令、串口/Host 日志、trace 和已知限制，并再次检查标识与有效载荷脱敏。
