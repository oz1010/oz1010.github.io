AI 基础设施 / 推理工程师学习计划

目标岗位： AI Infrastructure Engineer / LLM Inference Engineer
学习方式： 项目与目标驱动，视频、课程和论文作为辅助
建议周期： 42 周（约 10 个月）
建议投入： 每周 12～20 小时；如果每周投入不足 10 小时，可按比例延长
最终成果： 独立实现一个轻量级 LLM 推理平台 MiniInfer，并具备阅读、分析和优化成熟推理引擎的能力。

1. 学习目标与能力画像

最终目标不是成为通用 AI 应用开发者，也不是以训练算法研究为主，而是能够理解并优化大模型从模型执行、GPU Kernel、显存管理、请求调度到在线服务的完整推理链路。

1.1 核心能力

能力领域 需要达到的水平

C++ / Python 能编写可靠的系统组件、测试和实验工具 深度学习基础 理解 Tensor、自动微分、Transformer 和推理流程 GPU 架构 理解 SM、Warp、寄存器、Shared Memory、HBM、Occupancy CUDA / Triton 能实现、调试和优化常见 GPU Kernel 推理计算 理解 Prefill、Decode、Attention、KV Cache 推理优化 掌握 Kernel Fusion、FlashAttention、量化和显存优化 推理系统 理解 Continuous Batching、调度、请求管理和缓存 分布式推理 理解 Tensor Parallel、通信原语和通信开销 工程化 能构建 API 服务、监控、Benchmark 和可复现部署

1.2 学习原则

  1. 先做出最小可运行版本，再逐步优化。
  2. 每项技术都要有实验和量化结果。 不以”看完课程”作为完成标准。
  3. 先单 GPU，再多 GPU；先正确性，再性能。
  4. 优先理解数据流、内存流和执行流。
  5. 阅读成熟项目源码，但不要一开始就试图复刻整个 vLLM 或 TensorRT-LLM。

2. 总体路线与时间安排

阶段 周期 核心主题 项目 / 交付物

0 第 1 周 开发环境与工程工具 可复现开发环境

1 第 2～5 周 Python、C++、Linux、数学与 ML 实验集 ML 基础

2 第 6～9 周 PyTorch、Transformer、LLM MiniGPT 原理

3 第 10～15 周 GPU 架构、CUDA、性能分析 CUDA Operator Lab

4 第 16～21 周 LLM 推理引擎基础 MiniInfer

5 第 22～27 周 Kernel、量化、KV Cache 优化 Kernel Benchmark / Paged KV Cache

6 第 28～33 周 调度、批处理与分布式推理 MiniScheduler / MiniTP

7 第 34～36 周 生产级推理服务 Inference Server

8 第 37～42 周 综合项目与源码研究 MiniInfer 完整版 ————————————————————————————

时间安排是参考值。每个阶段应以验收标准为准，不要为了赶进度跳过正确性测试和性能分析。

阶段 4：实现自己的 LLM 推理引擎

周期：第 16～21 周

核心项目：MiniInfer

目标

构建一个支持真实 Decoder-only 模型加载和文本生成的轻量推理引擎。

4.1 理解推理过程

Prefill

  • 一次处理整个输入 Prompt。
  • 并行计算输入序列的表示。
  • 计算并写入各层 K/V。
  • 生成第一个输出 Token 的 Logits。

Decode

  • 通常每一步处理一个新 Token。
  • 读取历史 KV Cache。
  • 计算下一个 Token。
  • 更新 KV Cache，直到 EOS 或达到生成长度。

两阶段性能特征不同：Prefill 通常有较高的并行计算量；Decode 更容易受显存带宽、访存和批处理效率影响。

阶段 5：推理性能优化

周期：第 22～27 周

核心项目：Kernel Benchmark / Quantization Lab / Paged KV Cache

5.1 CUDA Kernel 优化

针对 Transformer 常见算子进行优化：

算子 优化方向

GEMM Tiling、Tensor Core Attention FlashAttention Softmax Online Softmax、Fusion RMSNorm Kernel Fusion RoPE Fused RoPE MLP GEMM Fusion Sampling GPU Sampling

重点理解 FlashAttention 的 IO-aware 思想：通过分块计算和在线 Softmax，减少 HBM 与片上存储之间的数据搬运。

学习：

  • 标准 Attention。
  • Attention 的计算和显存复杂度。
  • Tiling。
  • Online Softmax。
  • FlashAttention 的分块机制。
  • FlashAttention 与普通 Attention 的性能差异。

5.2 Triton

CUDA C++ 用于精细控制 GPU；Triton 适合快速开发和调优自定义 Kernel。

学习顺序：

  1. Vector Add。
  2. Softmax。
  3. Matrix Multiplication。
  4. LayerNorm / RMSNorm。
  5. Fused Attention。
  6. Persistent Matmul。

资料：Triton Tutorials

5.3 项目：LLM Kernel Benchmark

对每个算子保留：

  • PyTorch Reference。
  • Triton Implementation。
  • CUDA Implementation。

测试维度：

算子 测试维度

GEMM 不同 M / N / K Softmax 不同序列长度 RMSNorm 不同隐藏层维度 Attention 不同 Batch、Head、Sequence RoPE 不同位置长度 KV Cache 不同上下文长度

记录 Mean、P50 / P95 Latency、TFLOPS、Effective Bandwidth、Peak Memory 和 Numerical Error。

5.4 量化

学习顺序：

  1. FP32、FP16、BF16。
  2. INT8、INT4、FP8 的基本表示。
  3. Weight-only Quantization。
  4. Per-Tensor、Per-Channel、Group-wise Quantization。
  5. Scale、Zero Point、Calibration。
  6. SmoothQuant、GPTQ、AWQ 的基本思想。

项目：Quantization Lab

对同一模型比较 FP16、INT8、INT4：

  • 权重大小。
  • 峰值显存。
  • Decode 延迟。
  • 吞吐量。
  • 输出质量。

不要预设 INT4 一定更快。实际性能取决于 GPU、Kernel、反量化开销和 Batch 大小。

5.5 KV Cache 优化

研究：

  • MHA、MQA、GQA 对 KV Cache 的影响。
  • KV Cache Memory Layout。
  • Paged KV Cache。
  • Prefix Caching。
  • KV Cache Quantization。
  • Cache Eviction。
  • Block Allocation。

项目：Paged KV Cache

要求支持多请求、不同长度上下文、Block 动态分配与回收、请求结束时释放资源。

推荐资料

  • FlashAttention
  • Triton Tutorials
  • CUDA Best Practices
  • SmoothQuant
  • GPTQ
  • AWQ

验收标准

  • 至少完成 3 个有实测收益的 CUDA / Triton 优化算子。
  • 理解并复现 FlashAttention 的核心机制。
  • 完成一种低精度推理方案。
  • 完成 Paged KV Cache 原型和正确性测试。
  • 输出可复现的性能报告。

阶段 6：高性能推理系统

周期：第 28～33 周

核心项目：MiniScheduler / MiniTP

6.1 请求调度与批处理

研究传统静态 Batch 的问题，以及 Continuous Batching 如何在每轮 Decode 后动态加入和移除请求。

学习：

  • Static Batching。
  • Dynamic Batching。
  • Continuous Batching。
  • Iteration-level Scheduling。
  • Prefill / Decode Scheduling。
  • Chunked Prefill。
  • Request Priority。
  • Admission Control。

项目：MiniScheduler

实现：

  1. 多请求并发接入。
  2. 请求队列。
  3. 动态 Batch 构建。
  4. Decode 迭代调度。
  5. KV Cache 分配与释放。
  6. 请求取消和超时。
  7. 请求优先级。

关键指标：

  • TTFT（Time To First Token）。
  • TPOT（Time Per Output Token）。
  • End-to-End Latency。
  • Token Throughput。
  • Request Throughput。
  • P50 / P95 / P99 Latency。
  • GPU Utilization。

注意：吞吐量和延迟不是同一个优化目标。提高 Batch 大小可能提高总吞吐量，同时增加单请求等待时间。

6.2 分布式推理

先理解：

技术 作用

Data Parallelism 多份模型处理不同请求 Tensor Parallelism 将模型矩阵计算拆分到多个 GPU Pipeline Parallelism 将不同模型层放到不同 GPU Expert Parallelism 分布式执行 MoE 专家 Context Parallelism 分布式处理长上下文

优先学习 Tensor Parallelism：

  • AllReduce、AllGather、ReduceScatter。
  • NCCL。
  • GPU P2P。
  • PCIe、NVLink。
  • Communication / Computation Overlap。
  • 通信开销与计算规模的关系。

项目：MiniTP

先将 Linear Layer 拆分到两个 GPU：

  • Column Parallel Linear。
  • Row Parallel Linear。
  • AllReduce。
  • 分布式模型加载。

然后尝试将 Transformer 的 Attention 和 MLP 分布到多个 GPU。

只有单 GPU 时，可以先完成接口和模拟测试；真实通信性能必须在多 GPU 环境验证。

6.3 阅读成熟推理引擎

优先阅读：

  1. vLLM：PagedAttention、Scheduler、KV Cache、Continuous Batching、Tensor Parallel。
  2. TensorRT-LLM：In-flight Batching、KV Cache、量化、推测解码和分布式推理。
  3. SGLang：推理调度、RadixAttention 和结构化生成等。
  4. llama.cpp：轻量推理、量化和跨硬件部署。

不要从头通读整个仓库。围绕一个具体问题，沿调用链阅读相关代码，并画出数据流和关键结构。

验收标准

  • MiniScheduler 能管理多请求并发推理。
  • 能解释 Continuous Batching 和 Paged KV Cache 的实现机制。
  • 能解释 Tensor Parallel 的计算拆分与通信成本。
  • 能用实验比较不同并发负载下的延迟和吞吐量。

3.1 固定开发循环

例如学习 CUDA GEMM：

  1. 先用 CPU 实现矩阵乘法。
  2. 用最简单的 CUDA Kernel 实现。
  3. 测量运行时间。
  4. 学习 Shared Memory。
  5. 优化访存。
  6. 实现 Tiling。
  7. 使用 Tensor Core。
  8. 比较优化前后的性能。

不要先看完大量课程再开始写代码。

3.2 每个项目的 Definition of Done

一个任务只有满足以下条件才算完成：

  • 有明确的输入、输出和边界条件。
  • 有正确性测试。
  • 有性能基线。
  • 有优化前后对比（适用时）。
  • 有复现步骤。
  • 有简短设计说明。
  • 代码和实验记录已提交版本控制。

8. 最终执行建议

不要一开始就同时推进所有阶段。先集中完成三个核心项目：

里程碑一：MiniGPT

从零实现 Transformer、Attention、KV Cache，真正理解模型推理。

里程碑二：CUDA Operator Lab

使用 CUDA 实现 GEMM、Softmax、RMSNorm、Attention，掌握 GPU 性能优化。

里程碑三：MiniInfer

把模型、CUDA、KV Cache、调度和服务整合成一个完整推理引擎。

其他课程、论文和工具都围绕这三个项目展开。

建议将学习过程作为长期工程项目管理，每个阶段维护：

如果使用敏捷开发，可以按 1～2 周一个 Sprint：每轮选取少量优先任务，完成实现、测试、性能验证和复盘，再进入下一轮。

最终衡量标准：不是会使用 vLLM，而是当某条推理路径性能不理想时，能够通过源码、GPU Profiler 和实验定位原因，理解瓶颈，并尝试实现更好的方案。这才是 AI 基础设施 / 推理工程师真正需要具备的能力。
